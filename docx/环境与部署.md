# 运行环境与部署地址

项目区分**开发环境**和**生产环境**两套地址，构建时选定，代码里不写死任何域名或端口。
定义在 [`config/env.ts`](../config/env.ts)，由 [`rspack.config.ts`](../rspack.config.ts) 注入为前端全局常量。

## 两套环境

|                          | 开发环境（`pnpm dev`）                                     | 生产环境（`pnpm build`）                 |
| ------------------------ | ---------------------------------------------------------- | ---------------------------------------- |
| 前端站点                 | `http://localhost:8090`                                    | `https://chat.shunkai-dg.cn`             |
| 后端 API                 | `http://127.0.0.1:3000`（本地进程）                        | `https://api.shunkai-dg.cn`              |
| 认证前缀 `__AUTH_BASE__` | `/auth`（同源相对路径）                                    | `https://api.shunkai-dg.cn/auth`         |
| BFF 前缀 `__BFF_BASE__`  | `/v1`（同源相对路径）                                      | `https://api.shunkai-dg.cn/v1`           |
| `__WEB_ORIGIN__`         | `http://localhost:8090`                                    | `https://chat.shunkai-dg.cn`             |
| `fetch` credentials      | `same-origin`                                              | `include`                                |
| 跨域                     | 不跨域：devServer 把 `/auth`、`/v1`、`/api` 代理到本地后端 | 跨域：`chat.` 直连 `api.`，需要后端 CORS |

开发环境之所以写相对路径，是为了让浏览器认为是同源请求：本地后端不需要配 CORS、不需要
`credentials`，`localStorage` / Cookie 也不受第三方限制。生产环境前端和后端是两个子域名，
只能跨域访问，`credentials` 自动切成 `include`。

## 命令

```bash
pnpm dev          # 开发服务器，接口代理到本地 127.0.0.1:3000
pnpm build        # 生产构建（rspack build 默认 NODE_ENV=production，走域名）
pnpm build:prod   # 同上，显式指定，供 CI 表意清晰
pnpm build:dev    # 用本地地址打开发包（内网联调、给测试同学本地起后端时访问）
```

`pnpm dev` 每次启动、`pnpm build` 每次构建都会打印一行实际生效的地址：

```text
[env] APP_ENV=production WEB_ORIGIN=https://chat.shunkai-dg.cn AUTH_BASE=https://api.shunkai-dg.cn/auth \
      BFF_BASE=https://api.shunkai-dg.cn/v1 API_ORIGIN=https://api.shunkai-dg.cn credentials=include (cross-origin api)
```

## 选择环境

`config/env.ts` 读取环境名的顺序：

1. `process.env.APP_ENV`
2. `process.env.NODE_ENV`：rspack CLI 在加载配置文件**之前**写好，`serve`/`dev` → `development`，
   `build`/`preview` → `production`；`--node-env <value>` 可以在 CLI 上覆盖它
3. `.env` / `.env.local` 里的 `APP_ENV`（用于在不设 shell 环境变量时固定本机环境）
4. 都没有时兜底 `development`

只有值为 `production` 才使用生产域名，其他任何值都按开发环境处理，避免拼错环境名时
误把本地地址打进线上包。

注意 `--env KEY=VALUE`（rspack CLI 的通用参数）只传给「导出函数形式的配置文件」，
不会写进 `process.env`；本项目配置文件导出的是对象，所以切换环境用 `--node-env` 或真实环境变量。

## 覆盖默认值

`.env` 文件只在构建期读取，不会打进产物（产物里只有解析后的字符串）。按顺序合并，
后面的覆盖前面的；真实环境变量始终最优先：

```text
.env → .env.local → .env.<APP_ENV> → .env.<APP_ENV>.local
```

| 变量                            | 作用                     | 示例                             |
| ------------------------------- | ------------------------ | -------------------------------- |
| `APP_ENV`                       | 强制环境名               | `production`                     |
| `WEB_ORIGIN`                    | 前端站点地址             | `https://chat.shunkai-dg.cn`     |
| `API_ORIGIN` / `BACKEND_ORIGIN` | 后端根地址               | `https://api.shunkai-dg.cn`      |
| `AUTH_BASE`                     | 认证前缀，相对路径=同源  | `https://api.shunkai-dg.cn/auth` |
| `BFF_BASE`                      | BFF 前缀，相对路径=同源  | `https://api.shunkai-dg.cn/v1`   |
| `API_CREDENTIALS`               | 覆盖 `fetch` credentials | `include` / `same-origin`        |
| `DEV_API_TARGET`                | devServer 代理目标       | `http://127.0.0.1:3000`          |
| `DEV_PORT`                      | devServer 端口           | `8090`                           |
| `BASE_PATH`                     | 部署子目录               | `/app/`                          |

`AUTH_BASE` / `BFF_BASE` 支持三种写法，构建期统一归一化（去重斜杠、去尾斜杠）：

```ini
# .env.production
AUTH_BASE=https://api.shunkai-dg.cn/auth   # 完整地址：跨域直连
BFF_BASE=/v1                                # 相对路径：同源，由 chat 域名的 Nginx 反代
API_ORIGIN=api.shunkai-dg.cn                # 裸域名：自动补 https:// 并拼接默认前缀
```

本地后端端口不是 3000 时，写 `.env.development.local`（已被 `.gitignore` 忽略）：

```ini
DEV_API_TARGET=http://127.0.0.1:4000
```

同源反代部署（前端 Nginx 把 `/v1`、`/auth` 转到后端）想省掉 CORS 时：

```ini
# .env.production.local
BFF_BASE=/v1
AUTH_BASE=/auth
```

## 生产环境需要后端配合的事

跨域直连需要后端（auth-demo）配合，现已在应用层实现（`src/middleware/cors.js`），
通过环境变量 `CORS_ORIGINS` 开关，同源反代时留空即完全直通：

1. 后端容器/进程设置 `CORS_ORIGINS=https://chat.shunkai-dg.cn`（逗号分隔多个来源）。
   命中白名单时后端回显具体来源 `Access-Control-Allow-Origin`（不是 `*`，带凭证时浏览器
   拒绝通配）与 `Access-Control-Allow-Credentials: true`，因为前端 `credentials` 是 `include`。
2. 预检 `OPTIONS` 已放行方法 `GET/POST/DELETE`，头 `Authorization`、`Content-Type`、`Accept`、
   `X-Request-Id`、`X-File-Name`、`X-File-Mime`（后两个是原件上传用的自定义头），并回 204。
3. 后端使用 Opaque Bearer Token，**不使用 Cookie**，因此没有 SameSite 跨站 Cookie 问题；
   `credentials: include` 只是为签名票据等 Cookie 场景预留。
4. 非白名单来源的预检返回 403，普通请求不加 CORS 头，由浏览器拦截。
5. SSE 走 `GET /v1/chat/stream`，反代仍需关闭缓冲（`proxy_buffering off`）并放宽读超时。

图片原件的签名地址（`/v1/files/content?state=...`）由 `<img>` 直接加载，属于跨域子资源：
浏览器不带 Origin 时后端不加 CORS 头也能正常显示；若要画进 canvas（导历史 ZIP、
Mermaid 导出）才需要 CORS 允许头，此时请让前端带上 Origin 或给该响应固定放行。

## Nginx 参考配置

前端 `chat.shunkai-dg.cn`：

```nginx
server {
  listen 443 ssl;
  server_name chat.shunkai-dg.cn;
  root /srv/chat-demo/dist;

  # 会话地址是真实路径 /chat/<id>，直链和刷新都要回落到 index.html
  location / {
    try_files $uri $uri/ /index.html;
  }

  location ~* \.(js|css|woff2?)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
  }
}
```

后端 `api.shunkai-dg.cn`：

```nginx
server {
  listen 443 ssl;
  server_name api.shunkai-dg.cn;

  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;

    # 流式续推
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_read_timeout 3600s;
    chunked_transfer_encoding on;
  }
}
```

若采用同源反代（`chat.` 下转发 `/v1`、`/auth`），前端产物要用
`BFF_BASE=/v1`、`AUTH_BASE=/auth` 重新构建，否则浏览器仍会打 `api.` 域名。

## CI

`pnpm build` 即生产包，GitHub Pages 工作流无需额外变量；需要临时改地址时在
workflow 里加 `APP_ENV`、`WEB_ORIGIN` 等环境变量，或在仓库放 `.env.production`
（不含密钥，`.env*` 已被忽略，只有 `.env.example` 入库）。
